# Milestones 2–5: cloud acceptance and runtime handoff

The first milestone is the approved plan's slices 1–3: two players can build together, and the owner can leave and reliably resume after a confirmed save. The remaining four slices define milestones 2–5 below. This is one application, Driftwood Isles; the milestones do not create separate games.

The initial implementations shipped in alpha.1. Alpha.2 improved recovery and release reliability. Alpha.3 closes guidance defects and adds explicit acceptance evidence for the remaining milestones. Existing functioning features are retained, not described as newly implemented.

## What cloud completion means

The acceptance suites execute production rules, coordination, persistence, and presentation code. Fixtures supply only unavailable boundaries such as time, character facts, storage transport, and GUI effects. They do not run Roblox clients or simulate the engine. Sequential requests exercise the atomic, non-yielding purchase boundary; they are not evidence of measured network concurrency.

The release ZIP contains `cloud-validation.json`, generated by the successful full validation command. It identifies the tested file bytes, the verified place, completed check stages, and explicitly pending engine/device checks. Packaging rejects missing or stale evidence, changed inputs, or a different place. This report is an auditable record, not a cryptographic attestation that a trusted machine ran tests; use the matching GitHub Actions run as the execution record.

The source and place remain an **alpha prerelease**, not a Roblox public launch. No live experience has been published by the cloud workflow. No 30 FPS or pacing target is marked passed without device measurements.

## Runtime handoff

Use the complete [Studio/device checklist](studio-validation.md), recording the tested release tag and commit. Prioritize:

1. One player completes campfire → bridge → beacon → storm without grants, then reloads saved progress in the dedicated test experience.
2. Two clients repeat the loop; then four clients complete and fail storms, revoke helpers, and disconnect the owner during an unfinished event.
3. A visitor observing a storm receives read-only guidance; paused/loading profiles show the correct recovery status and retain safe Crew controls.
4. Phone portrait/landscape and desktop controls are usable; record actual-phone frame rate and first-session timings.

Record results and unresolved failures in [validation.md](validation.md). Do not convert pending boxes into passes based on CLI compilation or the existence of a release.
